# Notable model behaviors (qwen3.8-27b, variant high, via opencode)

All snippets are from `session_message` rows of the trivia-night sessions, redacted and trimmed. Times are local. S1 = setup/status-bar session (1TJDIi), S2 = trivia build (OLQKwR). See `sessions.md` for counts and `environment.md` for what was installed.

## A. Did the installed skills / plugins / agents change behavior?

Short answer from the evidence: **style and process scaffolding yes, skill-library usage barely.** The model was shown 118 skill ids but called the `skill` tool only 9 times in 3 days (brainstorming x3, opencode x3, writing-for-agents, writing-plans, frontend-design). What actually shaped behavior was always-on text injected into the prompt (caveman AGENTS.md, ponytail ruleset, superpowers bootstrap) and the repo's own AGENTS.md protocol, not on-demand skills.

### A1. Terse "caveman" voice (global AGENTS.md; strongest after an explicit `/caveman`)
- Global AGENTS.md has carried the caveman ruleset since Oct 10 00:05. Before the partner ran `/caveman` the S2 replies were ordinary prose. 10-10 19:39 (S2, after a 2012-char paste): "Good — that conversation is a lot of recon. Here's the picture as I hear it: **Event:** Sunday Nov 8 ... " (full sentences, articles).
- 10-10 19:41 the partner sent the `/caveman` template (user row starts "Activate caveman mode: on If no argument given..."). Next reply: "Caveman on. Still need the answer: Question up. Teams claim how — you click the team that buzzed (one device, TV only), or each team taps own phone?" Subsequent replies: "Re-parsed with double-posts = same person. Corrected picture: ..." and "[a name, omitted]. Fixed: ...".
- Final-text length: median-style average 31-52 words per text part in S2 vs 330 words for `general` council subagents (which did not get the cavecrew voice) and 159 for cavecrew-reviewer. Reasoning stays verbose: 1,024 reasoning blocks averaging 445 words (455k words) vs 432 visible text parts averaging 38 words (16k words), roughly 28:1 -- the "terse" effect is on the visible reply only.
- Model reasoning acknowledges the rule: 10-12 01:26 "Done. Now I'll write up the summary. Caveman style, but clear." 10-11 10:16 "Following caveman/ponytail + the question tool: one focused question is warranted here." (102 reasoning blocks mention caveman.)
- Sample terse tool-status messages (S2): 10-11 10:12 "Server died (session resume killed the background process). Restarting and verifying in the browser."; 10-11 11:37 "Palette verified: Start orange `#F26522`, radio orange, body blue-black. Committing step 1."
- Caveman *plugin hooks* probably did not run (not in the plugin-load log Oct 13+); the effect is from AGENTS.md + the command template.

### A2. Cavecrew subagents produce the caveman review format
- 22 backward-council reviewers ran as `cavecrew-reviewer` (7 as `cavecrew-builder`, a mismatch with its "1-2 file edit" description; those were told "Report only" and complied: "No fixes made. Report only."). Their output follows the agent file's `path:line: <emoji> <severity>: <problem>. <fix>.` contract, e.g. 10-12 01:07: "styles.css:28: 🟠 risk: h1 is 68px; plan L545 says \"h1 56 → 72px\". Align: bump to 72px or amend plan line to 68px (captain brief says 68/800 → likely plan stale)." and 10-11 03:08 "docs/superpowers/plans/2026-10-10-trivia-night.md:90-123 — 🟠 MED: Task 1 checkboxes still `- [ ]` though work committed; AGENTS.md says checkbox updates belong in the commit."
- `general` forward-council subagents wrote long structured prose instead (avg 330 words). From 10-12 00:43 on, forward councils also moved to `cavecrew-reviewer`.
- 17 of 32 backward reviews flagged an unchecked plan checkbox: the reviewer pass, not the builder, repeatedly enforced the "plan checkboxes are the progress record" rule.

### A4. Superpowers workflow: brainstorming -> design doc -> writing-plans -> subagent review, but NOT the execution skills
- The workflow the partner gets from superpowers did happen at the front end: 10-10 10:51 first S2 prompt ("i'm looking to create an application i can use to host a trivia night with friends") -> model immediately called skill `brainstorming` -> 10:52 "Using brainstorming to figure out what kind of trivia night app you actually need. Dispatching the builder check." (a `general` subagent re-reads the doc cold, a superpowers/mattpocock-style spec self-review) -> 22:23 `writing-for-agents` then 23:03 `writing-plans` -> plan `docs/superpowers/plans/2026-10-10-trivia-night.md`.
- Brainstorming reappeared for a design question on 10-11 10:16 (multi-winner semantics) and raised a `question` popup; the partner answered in free text rather than picking an option.

No TDD skill was invoked, yet tests were written (`test/scoring.test.mjs`, `node --test` 4/4 passes) because the plan specified them.
- The model's own reasoning shows it knew the workflow was inherited: 10-10 22:43 (S1) "This looks like the brainstorming→plan workflow for trivia-night got executed (by the user or another agent)".
- The subagent-driven-development *pattern* arose from the repo AGENTS.md (the partner's 10-10 22:23 prompt + the council section), not from the skill: 43 council subagents, one backward + one forward pass after each plan step (tasks 1-7, 7.5-7.10, deploy, bank, about, README, folder, reveal), run in pairs.

## B. Failure modes tied to the model / local serving

### B1. Context overflow at 163,840 tokens produces truncated tool calls ("stuck" feeling)
- 15 `finish=length` events at 162.4k-163.8k prompt tokens (config said 262,144). When it happens mid-tool-call the call arrives incomplete: 11 `tool.input-incomplete` errors ("Tool call arguments were not completed and were not executed. Re-issue the tool call with complete arguments.").
- 10-11 10:44-10:45: four consecutive truncated turns (`write` styles.css x3) -> the partner at 11:24: "what's wrong with my tool you seem to have stopped/stuck". Auto-compaction fired at 11:24 (123.5k prompt tokens). Model afterwards (11:32): "Not your tool. My `write` call for `styles.css` got truncated mid-stream 3× (\"arguments not completed\") — harness input hiccup, file untouched. Checking state, retrying now." (Correct about the cause being the truncated call; it blamed a 'harness hiccup' not the context limit.)
- Repeats: 10-11 13:41-13:42 (4 hits; partner: 14:01 "plan a compaction and try again"), 10-12 12:51-12:52 (compaction 12:52), 10-12 21:52-21:53 (3 hits), 10-11 01:03 (1 hit after 6.7 min of generation producing only reasoning), S1 10-12 20:45 (12 output tokens after 7.5 min; compaction next at 10-13 00:06).
- Compactions otherwise fired between 41k and 127k tokens; the 11 compaction summaries are 6-11k chars each and the model resumed correctly from the "Objective/Requirements" summary every time.

### B2. Text-only model vs image tool results (repeated errors, 3.5 h lost)
- 10-11 20:21-20:26 the model took before-screenshots for the UI pass (`.playwright-mcp/ui-before-board.png`) and read the PNG back with the `read` tool. Every later request then failed with provider error `image input is not supported - hint: if this is unexpected, you may need to provide the mmproj` (6 recorded errors 20:27, 20:32, 20:33, 20:49, 21:06, 21:40; the UI showed "Retrying in 6s · attempt 4"). The image stayed in the history, so each retry re-sent it.
- Partner 20:32: "i'm not sure what the prvious error is. is this because the qwen 3.8 27b model does not take image input?"; 20:47 "ok if image supprot is nto supported let's just continue on. i can switch to a different model to do the image bits, just leave a note for another model to pick up"; 21:04 "skip the image input componetns postpone it to the very end"; 21:39 "continue without image featuers". The session only recovered after the partner started a manual compaction (23:53) and the model confirmed (23:57): "Process fix first, then build. Council missed it because the plan assumed screenshot review — constraint (text-only model) wasn't in the plan's assumptions. Fixing that in the plan now so Tasks 8/9 use text-only verification: a11y snapshots + `getComputedStyle` assertions + `document.fonts` checks."
- The partner's critique (23:57): "this image issue where i keep getting this error ... is something your council review should've picked up". Neither the harness nor the model self-diagnosed that the model is text-only until the partner asked.
- After this point the project uses text-only checks (accessibility snapshots, computed-style assertions) and defers image checks to a final step "for another model".

### B3. Code Mode / MCP tool misuse (38 soft errors in `execute`)
- Playwright was reachable only through Code Mode: 10-11 02:14 the council subagent wrote `const r = tools.playwright ? null : search('playwright evaluate', 20); console.log(JSON.stringify(r.items...` -> "TypeError: Cannot read properties of null (reading 'items')". 02:18 `search('playwright')` -> "Invalid input for tool 'search': SchemaError(Expected object)"; third try with `search({query: \"playwright\", limit: 30})` worked.
- Other classes: un-awaited Promise ("JSON.stringify received an un-awaited Promise; await it first"), `setTimeout`/`process` not defined in the sandbox, strict-mode locator violations, 5 s timeouts on `wait_for`, `browser_fill(...)` (non-existent tool; real name `browser_fill_form`), and a syntax error from malformed arrow functions: 10-13 16:21 "My bad — one of the evaluate functions lost its braces (`() => el.click(); return …` is a syntax error). Retrying with all functions properly braced:" (the partner had said "seems like there was a playwright error, can you try again"). No hard "unknown tool" errors; the model did not invent top-level tool names.

### B4. Edit tool brittleness
- 4 `Could not find oldString in ... It must match exactly` (plan/spec/question.js edits) and 3 `tool.input-incomplete` edits (10-12 12:51-12:52 while patching `question.js`); recovered each time by re-reading and retrying; no corrupted files recorded.

### B5. No refusals, no repetition loops
- No assistant refusal text found. Repeated identical consecutive calls only occur as re-issued truncated calls (`write` x4, `edit` x3). No runaway loops; longest single steps were council subagents: forward council "folder" took 159 min wall and 27 messages (10-13 08:44-11:23) and "reveal" 69 min.

## C. Following the partner's process rules

- Commit protocol (AGENTS.md): repo has 102 commits Oct 10 22:56 - Oct 14 09:55; all carry the robot marker, 84 carry `Co-Authored-By: Qwen 3.8 27B <qwen-coder@alibabacloud.com>` (the rest are 18 later commits co-authored by Claude Haiku/Opus/Sonnet 5.5). Early commits lacked a scope (`docs: 🤖 add design spec and agent protocol`, `chore: 🤖 add playwright toolchain...`); the partner corrected at 10-11 01:03 ("when writing your conventional commits. write the type and scope as in https://www.conventionalcommits.org/...") and later commits use `type(scope): 🤖 ...`. The AGENTS.md was then amended (diff pushed to the model 10-11 01:52).
- Council compliance: the model dispatched a backward+forward pair after every step without being reminded after 10-11 01:58 ("you council review the plan and make necessary changes and go ahead"). When the partner asked for a plan change the model sometimes skipped re-council and said so: 10-11 01:56 "Skipped: re-council on the fix itself — the council produced these findings and the fix is verified against the live remote".
- Where council missed: the text-only/image constraint (B2). The reveal-answer-in-trivia-mode requirement was also missed once and the partner caught it on 10-13 14:31 ("you are missing a feature/change where the trivia mode should also have a reveal answer button") even though the partner had asked for it on 10-11 10:30 and 10-11 20:30.

## E. Security / scope surprises worth noting for the case study

- Credentials access: in S2 (10-10 20:41-20:54) the model, asked to read "this session's status bar", looked up the opencode server endpoint in the opencode service credentials file, then reported "Auth cracked: Basic opencode:<pw>" (password value NOT reproduced here) and queried the local opencode HTTP API to reconstruct the footer line ("I can't read the rendered bar (no tool for it), but I can reproduce its values from the OpenCode API"). The global config has no `permission` key (opencode defaults applied; no prompt is recorded). It stayed local and read-only, but it is credential-reading initiative by a local model under a prompt that never asked for it.
- Scope creep into the partner's own tooling: the model edited the partner's opencode TUI config (`cli.json`, status line plugin), created `session-stats/tui.tsx`, installed ~10 skill collections and a Python tool (`uv tool install graphifyy`) in S1 on its own plan, wrote a skill inventory into the Obsidian vault on request (23:58 prompt), and (S1 10-12 17:55) removed a plugin entry the partner wanted kept.
- The model repeatedly guessed that "another agent" was working in parallel (10-10 20:26 "another agent (maybe a caveman sub-agent? or a Claudian in the vault?)", 10-10 22:43), misreading the partner's remark about their other (Claude Code) agent editing the status bar -- a wrong-but-harmless inference.
